From orchestration/defs/unverified_customers_cy/defs.yaml — six typed facts; everything else derives or defaults, and the environment carries the coordinates (DATABRICKS_WAREHOUSE_ID + the service principal — the YAML never does).

  query_type: unverified_customers
  operator: cy
  job_name: Send_Email_to_NonVerified_CY_Customers

  schema_name: voperdb
  query: |
    select cusCustomerID as CustomerId, cusCompanyID as CompanyId
    from cCustomer ...   # the notebook's SQL, token-verbatim

The 13-field contract (validated 2026-10-26)

Transcribed from the team's kafka_message_publisher.ipynb; the field-by-field record and every decision live in docs/poc/JOBOTRON_CONTRACT_PARITY.md.

JobId           <JobName>_<CompanyId>_<yyyyMMddHHmmss UTC>
JobName         the YAML's job_name — the wire identity
JobCreated      second-truncated UTC
RunId           the Dagster run id
CompanyId       from the row
CustomerId      the key, cast to string
ItemsCount      the batch total
ItemNumber      row_number over CustomerId (deterministic tie-break)
ItemId          <ItemPayloadHash>-<ItemNumber>
ItemPayload     every result column, nested
ItemPayloadHash sha256 over the pinned canonical JSON
IsDryRun        the run's mode
SchemaVersion   1

Guarantees

  • The query must emit CustomerId and CompanyId — a result missing them fails the run, named, before any produce.
  • Hash canon: compact separators, result-column order, nulls explicit, non-ASCII kept — the exact bytes the wire carries.
  • GDPR: the payload is exactly the query's columns; real topics would run TLS in transit and bounded retention.

Components and jobs

One Dagster component (orchestration/components/reverse_etl_jobotron.py), three instances (orchestration/defs/unverified_customers_{cy,gr,ro}/). Per instance: the setup asset (the topic only — a no-op under dry-run, not even a Kafka connection), the publish asset, the consume asset (decode, dedup on ItemId, mirror), plus setup and reset jobs. The instances own nothing in Databricks — read-only SELECTs on de.voperdb; a topic exists only once a run carries dry_run: false. Design: docs/poc/JOBOTRON_CONTRACT_PARITY.md and docs/poc/REVERSE_ETL_JOBOTRON.md.

Show the publish asset's pipeline 
resolve the warehouse id (DATABRICKS_WAREHOUSE_ID — env, never YAML)
submit the YAML query VERBATIM in the YAML's catalog.schema context (Statement Execution API, 50s inline wait)
poll to a terminal state; fetch every result chunk (completeness-verified)
coerce values back per the manifest's declared types (JSON_ARRAY stringifies)
build_messages: order by CustomerId, hash per the pinned canon, 13 fields
dry-run gate (the default): metadata only — items_count, previews, seconds
produce one JSON message per row (key = CustomerId) to the instance's topic
metadata: items_count, dry_run, schema_version, warehouse_id, statement_seconds
