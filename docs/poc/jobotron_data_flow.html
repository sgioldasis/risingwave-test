Jobotron producer — data flow

Runs the candidate-selection query from jobotron.yaml against the demo tables in Databricks and publishes one Avro message per selected customer to its operator topic — no Spark, no JVM, no Databricks compute. A demo consumer then mirrors each topic into a Postgres table per operator; the RFC's real worker (dedup, eligibility re-validation, actions) remains Accounts & Payments scope. Use the buttons, click a step, or press the left and right arrow keys.

Buttons need the helper: run ./bin/3_run_reverse_etl_demo.sh and open http://localhost:4002/jobotron

    The demo tables

    Created by the setup job from orchestration/defs/reverse_etl_jobotron/defs.yaml. Both are plain Delta with no Change Data Feed — the producer reads each table's current snapshot with delta-rs, so the CDF machinery (and the delta-rs CDF gap that pins the CDF syncs to Spark) never applies. There is no state table: the full eligible set is published every run and the worker deduplicates, so the producer stays stateless.

    • Customers carries the routing column: operator picks the topic, and an unknown value fails the run — nothing ever publishes cross-market.
    • KYC cases holds one row per customer with its current case status. The demo query is the RFC's example job: send PM to customers that remain unverified — active customers joined to their PENDING case.
    • Deletion vectors are off to keep the read path uniform with the other demo tables; column mapping is off because this demo has no drop/rename ops.
    • The segment changes without tombstones: verify or deactivate a customer and it simply stops appearing at the next publish — full-snapshot semantics. The worker's own dedup (Redis markers) and eligibility re-validation make republishing safe (RFC: "Safe Execution").
    • GDPR: the payload is exactly the query's columns (payload minimization by construction) plus run_id and job_type; the real topics would run TLS in transit (the RFC's stated mitigation) and 10-day retention.
    • The demo consumer (step 4) is a Dagster asset that re-reads each topic from the beginning, keeps the last message per customer_id, and rebuilds jobotron_demo_<operator> in the demo Postgres (the same database the Debezium sink writes). Rebuild-per-consume mirrors state; a real worker would act per message and keep its own state instead.

    Tables (the setup asset's DDL)

    CREATE TABLE IF NOT EXISTS
  de_dev.sr_poc_external.reverse_etl_jobotron_customers (
  customer_id BIGINT NOT NULL,
  email STRING,
  locale STRING,
  operator STRING,
  is_active BOOLEAN
) USING DELTA
TBLPROPERTIES ('delta.enableDeletionVectors' = 'false');

CREATE TABLE IF NOT EXISTS
  de_dev.sr_poc_external.reverse_etl_jobotron_kyc_cases (
  customer_id BIGINT NOT NULL,
  status STRING,
  updated_at TIMESTAMP
) USING DELTA
TBLPROPERTIES ('delta.enableDeletionVectors' = 'false');

    The job's YAML (orchestration/defs/reverse_etl_jobotron/defs.yaml)

    type: orchestration.components.reverse_etl_jobotron.JobotronProducer
attributes:
  job_type: kyc.unverified_pm
  operators: [gr, br]
  topic_template: "jobotron_demo_{operator}"
  query: |
    SELECT c.customer_id, c.email, c.locale, c.operator
    FROM customers AS c
    JOIN kyc_cases AS k ON k.customer_id = c.customer_id
    WHERE k.status = 'PENDING' AND c.is_active

    Components and jobs

    One Dagster component (orchestration/components/reverse_etl_jobotron.py): the setup job creates the tables, topics and seed; the publish asset runs the whole query-to-Kafka path in one Dagster run — delta-rs scans and DuckDB, no JVM, 0.0 warehouse seconds; the change ops edit the demo data; the reset job tears the topics, subjects and tables down. Design and RFC context: docs/poc/REVERSE_ETL_JOBOTRON.md.
