The demo tables

Created by the setup job. Both are plain Delta with no Change Data Feed — the producer reads each table's current snapshot per the job's scan_engine knob (delta-rs snapshots, or the DuckDB delta extension's streaming delta_scan), so the CDF machinery (and the delta-rs CDF gap that pins the CDF syncs to Spark) never applies. No state table: the full eligible set is published every run and the worker deduplicates.

  • Customers carries the routing column: operator picks the topic; an unknown value fails the run — nothing publishes cross-market.
  • KYC cases holds one row per customer. The query is the RFC's example job: send PM to customers that remain unverified.
  • The segment changes without tombstones: verify or deactivate a customer and it stops appearing at the next publish. The worker's dedup and re-validation make republishing safe (RFC: "Safe Execution").
  • GDPR: the payload is exactly the query's columns plus run_id and job_type; real topics would run TLS in transit and 10-day retention.
  • The demo consumer rebuilds jobotron_demo_<operator> from the messages of the latest publish run only — topics append, so grouping by the last message's run_id is what keeps the table the current segment.

The job's YAML

From orchestration/defs/reverse_etl_jobotron/defs.yaml — the query, routing, and identifiers are data, not code.

type: orchestration.components.reverse_etl_jobotron.JobotronProducer
attributes:
  job_type: kyc.unverified_pm
  operators: [gr, br]
  topic_template: "jobotron_demo_{operator}"
  query: |
    SELECT c.customer_id, c.email, c.locale, c.operator
    FROM customers AS c
    JOIN kyc_cases AS k ON k.customer_id = c.customer_id
    WHERE k.status = 'PENDING' AND c.is_active

Components and jobs

One Dagster component (orchestration/components/reverse_etl_jobotron.py): the setup job creates tables, topics and seed; the publish asset runs the whole query-to-Kafka path in one run — Delta scan + DuckDB (per-job scan_engine knob), 0.0 warehouse seconds; the change ops edit the demo data; the reset job tears it all down; the consume asset mirrors the topics into Postgres. Design and RFC context: docs/poc/REVERSE_ETL_JOBOTRON.md.
