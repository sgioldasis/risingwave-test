The instance's YAML

From orchestration/defs/unverified_customers/defs.yaml — ONE instance of the team's Jobotron component (the vendored APR-336 wheel): the three variant-A notebooks as a fan-out, the template carrying the notebooks' shared SQL and the per-market differences as data. {market} sits in table names, so it is a whitelist-validated literal; everything else binds as Statement Execution parameters. The environment carries the coordinates (DBT_DATABRICKS_HOST, DATABRICKS_WAREHOUSE_ID + the service principal — the YAML never does).

type: kaizen_dagster_jobotron.components.jobotron.JobotronComponent
attributes:
  name: unverified_customers
  asset_key_prefix: [jobotron]
  job_name: Send_Email_to_Unverified_Customers
  query_template: |
    select cusCustomerID as CustomerId, cusCompanyID as CompanyId
    from de.voperdb_{market_code}.cCustomer
    ...
    and cusCompanyID = {company_id}
  topic_template: "jobotron_unverified_customers_{market_code}"
  companies:
    include: [CYSTX, GRSTX, ROBTN]   # the exact comCodes — one partition per company
  parameters_by_company:
    CYSTX: {group_id: 1424, excluded_types: "2, 5, 6, 10, 11"}
    GRSTX: {group_id: 1425, excluded_types: "2, 5, 6, 10, 11, 15"}
    ROBTN: {group_id: 1321, excluded_types: "2, 5, 6, 10, 11"}
  literal_parameters: [market_code]
  workspace: "{{ env('DBT_DATABRICKS_HOST') }}"
  warehouse: "{{ env('DATABRICKS_WAREHOUSE_ID') }}"
  kafka_profile: openshift_kafka_connect
  message:
    format: envelope
    key_column: CustomerId
  schema_version: 1
  dry_run: true

The wire contract: the notebooks' 13-field envelope

One message per selected customer, keyed by the stringified CustomerId, byte-for-byte the KYC notebooks' kafka_message_publisher shape — ItemPayloadHash (sha2-256 of the compact payload), ItemNumber ordered by CustomerId, SchemaVersion: 1.

{"JobId": "Send_Email_to_Unverified_Customers_7_20261112053017",
 "JobName": "Send_Email_to_Unverified_Customers",
 "JobCreated": "2026-11-12T05:30:17Z", "RunId": "1fba69e5-…",
 "CompanyId": 7, "CustomerId": 490301250,
 "ItemsCount": 51, "ItemNumber": 1, "ItemId": "490301250",
 "ItemPayload": {"CustomerId": 490301250, "CompanyId": 7},
 "ItemPayloadHash": "9f2c…", "IsDryRun": true, "SchemaVersion": 1}

Guarantees

  • Keyed by the query's CustomerId column — the demo mirror dedups on the Kafka key, last write wins.
  • IsDryRun: true (the default) is what the Worker no-ops — the demo mirror skips those records too; RunId/JobCreated tie every message to the Dagster run that published it.
  • GDPR: the payload is exactly the query's columns; real topics would run TLS in transit and bounded retention.

Components and jobs

The publish asset is the vendored Jobotron component (kaizen-dagster-jobotron, APR-336), ONE fan-out instance (orchestration/defs/unverified_customers/) partitioned by exact comCode (CYSTX/GRSTX/ROBTN) — the demo UI launches it with the market's dagster/partition tag. The local side is demo plumbing only (orchestration/assets/reverse_etl_jobotron.py): the setup asset (the topic only — a no-op under dry-run, not even a Kafka connection), the consume asset (decode, skip dry-runs, dedup on the key, mirror), and the reset job. The instance owns nothing in Databricks — read-only SELECTs on de.voperdb; a topic exists only once a run carries dry_run: false. Design: docs/poc/JOBOTRON_KYC_NOTEBOOK_PATTERNS.md.
