</> What it is

A Rust implementation of the Delta Lake protocol with Python bindings. It reads the table straight from storage with a service principal.

🔍 What we use

The table version, any past version, each commit's file actions, the history for timestamps, and deletion-vector masks.

⚠ What we found

It cannot commit to warehouse-written v7 tables, and column-mapped sources need a direct parquet fallback. Both are handled in code.

ZERO-DBU REVERSE ETL07 / 18

Reading Delta changes without Databricks compute

Databricks SQL path (baseline)

◆table_changes()
  • • Needs Change Data Feed enabled on the source table. The Databricks notebook option relies on the same table_changes().
  • • Every sync meters DBUs: 4.97 on Oct 12 and 0.45 on Oct 13 while this path ran.
  • • With deletion vectors on, a 1-row delete made CDF emit 300,000 change rows for a 100k-row table.

delta-rs path (zero DBU)

☁➞0DBU
  • • No Change Data Feed needed: it works on any Delta table.
  • • Append-only commit: read only the new files.
  • • Rewrite commit: diff only the removed and added file pairs.
  • • Deletion vectors: apply each file's keep-mask at that version.
▣
Diffing per version is required: a key deleted in one commit and reinserted in the next must emit both events.

At-least-once, never a silent loss

producer.produce(..., on_delivery=collect_errors) undelivered = producer.flush( timeout=120) if undelivered or errors: raise RuntimeError(...)

produce() only queues the message. It returns before Kafka confirms. A failed send is reported later, in the background.

The flush waits and checks. The run waits up to 120 s for Kafka to confirm every message. Any failure stops it before the watermark moves.

The next sync sends it again. The watermark did not move, so the same versions are replayed. Nothing is skipped.

✓
Replays are harmless because both targets upsert by key. Producer tuning: lz4, 50 ms linger, one flush after the last chunk.

Zero Python files adopted. Teams drop YAMLs into their defs folders; the loader merges them.

No Dagster resources. One defs.yaml deploys to staging and production unchanged — values live in the environment (the env contract), never in the YAML.

Names derived by construction. Everything reverse_etl_<name>_<...> follows the label; typed fields are only what exists independently.

The watermark guard ships with it. A renamed label fails loudly instead of silently restarting; sync_name carries a watermark across a rename.

✓
The released components import nothing demo-shaped — pinned by an import-hygiene test, and by a compatibility test that loads them from a plain defs folder.

ZERO-DBU REVERSE ETL16 / 18

Where this approach stops

💡 CDF is still the better tool for

  • • Large, update-heavy sources with many commits per window.
  • • Sub-minute freshness. Each run here is a batch.
  • • Vendor-supported semantics instead of owned diff logic.

⚠ Still open in this pipeline

  • • Partitioned tables without deletion vectors fall back to a full-snapshot diff.
  • • The first sync is a backfill and reads the full history.
  • • Each sync walks the whole commit log once for timestamps.
ZERO-DBU REVERSE ETL17 / 18

Four bugs found live, now designed out

⚠ Deletion vectors and CDF

A 1-row delete emitted 300,000 change rows. Snapshot diffs are exact however files are rewritten.

🔒 Pin the schema to the commit

A rename between the data read and a live schema read silently nulled a populated column.

▣ Registries dedupe by content

Re-adding a column left an older schema as latest and RisingWave rejected it. Register until yours is latest.

🕑 History lies on pinned handles

delta-rs shifted version labels and gave wrong commit timestamps. Build the map from a current handle.
