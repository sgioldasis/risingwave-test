    The Databricks source table

    What the table behind step 1 needs, and how to define it. The setup job creates it for you from orchestration/defs/reverse_etl_avro/defs.yaml; this is the DDL it runs.

    • A Delta table with Change Data Feed on (the three UniForm syncs create it readable as Iceberg; the delta sync creates it plain Delta with column mapping — the dropdown shows which). The sync itself does not read the Change Data Feed: it reconstructs the changes from snapshot diffs with delta-rs (no Spark, no warehouse scans), so it only needs the table's Delta log. Keeping delta.enableChangeDataFeed on costs nothing and keeps the table compatible with the notebook comparison path, which does read table_changes().
    • A key column that never repeats and never changes. Here it is rid, an identity column Databricks fills in on insert. Every target is keyed on it. The business id is not used as the key: Unity Catalog primary keys are informational, so two rows can share an id, and deleting one removed the other downstream.
    • The key must exist from creation. An identity column cannot be added to an existing table, so adding it later means the reset job, then the setup job.
    • UniForm (optional; on for the avro/cdf/orders sources, off for the delta source). The extra properties let Iceberg readers query the same table. They need column mapping on and deletion vectors off, and must be set at creation, because turning them on later is a schema commit — harmless for the sync (the reconstruction diffs snapshots and handles schema changes natively), but a metadata-generation event for the Iceberg side. The Iceberg side is read-only.
    • Your own columns go in source_columns in the sync's YAML (here id, value, updated_at).
    • Inserts must list their columns, as in INSERT INTO t (id, value) VALUES (...). A column-less insert fails on a table with an identity column.
    • Schema changes: adding a column is carried to the targets, and so is dropping one (drop propagation is on for every sync): the sync diffs the source schema against the state table's recorded last_schema and drops the vanished column from RisingWave and Postgres too — RisingWave fills <col>_ts companions in first, Postgres follows the broader rule and also re-drops anything a sink replay re-added. Renames propagate as renames now: the state records each column's delta.columnMapping.id (stable across a rename), so the sync can tell the two apart — RisingWave gets add + update-copy + drop (no RENAME COLUMN there, but the data survives), Postgres a native rename plus an automatic sink task restart, because the JDBC sink's in-memory schema cache would fail the next message otherwise. Every source table is created with column mapping, so Delta accepts DROP COLUMN and RENAME COLUMN everywhere; type changes are still refused by Delta and stay out of scope.

    Source table

    CREATE TABLE IF NOT EXISTS
  de_dev.sr_poc_external.reverse_etl_avro_source (
  rid BIGINT GENERATED ALWAYS AS IDENTITY,
  id BIGINT NOT NULL,
  value STRING,
  updated_at TIMESTAMP
) USING DELTA
TBLPROPERTIES (
  'delta.enableChangeDataFeed' = 'true',
  'delta.columnMapping.mode' = 'name',
  'delta.enableDeletionVectors' = 'false',
  'delta.enableIcebergCompatV2' = 'true',
  'delta.universalFormat.enabledFormats' = 'iceberg'
);

    State table (the watermark, steps 2.1 and 2.5)

    CREATE TABLE IF NOT EXISTS
  de_dev.sr_poc_external.reverse_etl_avro_state (
  sync_name STRING,
  last_commit_version BIGINT
) USING DELTA
TBLPROPERTIES (
  'delta.columnMapping.mode' = 'name',
  'delta.enableDeletionVectors' = 'false',
  'delta.enableIcebergCompatV2' = 'true',
  'delta.universalFormat.enabledFormats' = 'iceberg'
);
